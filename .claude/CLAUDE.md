# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`soxspipe` is the data-reduction pipeline for the SOXS instrument (and shares a common codebase with X-Shooter, "xsh") — a Python package plus a `soxspipe` CLI tool. It reduces raw ESO FITS frames (bias, dark, flat, arc, science) through a full spectroscopic reduction cascade to wavelength- and flux-calibrated spectra.

## Commands

Install in dev mode:
```bash
pip install -e ".[dev]"
```

Run tests:
```bash
pytest                                    # the canonical suite: tests/ (pyproject sets testpaths = ["tests"])
pytest tests/unit tests/integration -m "not slow"   # the offline suite CI enforces
pytest -k "test_horne_extraction" --pdb -v -s       # single test, drop into debugger on failure
```

The real-data acceptance test is opt-in and needs a prepared workspace:
```bash
SOXSPIPE_REAL_DATA_DIR=/absolute/path/to/workspace pytest tests/real_data
```

Coverage floor is `fail_under = 70` in `pyproject.toml`; CI additionally enforces `diff-cover --fail-under=80` against `develop`.

The settings files `test_settings_soxs.yaml`, `test_settings_soxs_sim.yaml`, and `test_settings_xsh.yaml` live under `soxspipe/` and **are tracked in the repo**. They point at unit-test data on local disk (`~/xshooter-pipeline-data/`, `~/soxspipe-unittests/`) that is not distributed, so anything reading them fails in an environment that lacks that data.

Build docs (Sphinx):
```bash
cd docs && make html
```

CLI entry point is `soxspipe = soxspipe.cl_utils:main` (see `pyproject.toml`); usage/options are documented in the docopt docstring at the top of `soxspipe/cl_utils.py`.

## Architecture

### Two layers: recipes and the reducer

- **Recipes** (`soxspipe/recipes/*.py`) are the atomic reduction steps (`soxs_mbias`, `soxs_mdark`, `soxs_mflat`, `soxs_disp_solution`, `soxs_order_centres`, `soxs_spatial_solution`, `soxs_stare`/`soxs_nod`/`soxs_offset` [+ `_std` variants]). Every recipe subclasses `base_recipe` (`soxspipe/recipes/base_recipe.py`), which provides shared machinery: frame preparation (`prepare_frames`), trimming, clip-and-stack combination, detrending, QC helpers (RON, median flux level), FITS keyword updates, and product-path prediction/write-out. A recipe implementation typically only needs `verify_input_frames()` and `produce_product()`.
- Each recipe is driven by a **SOF (set-of-files) file** — a plain-text list of input FITS frames plus tags (e.g. `BIAS_UVB`) — rather than being called with ad hoc file lists. SOF association rules live in `soxspipe/resources/{soxs,xsh}_sof_map.yaml`.
- The **`reducer`** util (`soxspipe/commonutils/reducer.py`, exposed as `soxspipe reduce all`/`soxspipe reduce sof`) orchestrates running recipes over an entire workspace in the correct cascade order, with optional multiprocessing and automatic SOF rewriting if an expected upstream product is missing.
- The **`data_organiser`** (`soxspipe/commonutils/data_organiser.py`) is the backbone that prepares a raw workspace: uncompresses `.Z` frames, classifies raw frames, builds SOF sets/files, and predicts downstream product paths — all tracked in a SQLite database (`soxspipe.db`) with tables `raw_frames`, `raw_frame_sets`, `sof_map`, `product_frames`. See `docs/source/data_organiser_and_reducer/` for the full algorithm description and diagrams.
- QC metrics generated by each recipe are checked against `qc-acceptable-ranges` in the settings file; out-of-range QC forces a recipe "fail" so bad data doesn't cascade downstream.

### Instrument abstraction (SOXS vs X-Shooter)

The codebase supports both SOXS and X-Shooter via a settings-driven `instrument` key (defaults to `"soxs"`):
- `detector_lookup` (`soxspipe/commonutils/detector_lookup.py`) resolves detector parameters from `soxspipe/resources/{soxs,xsh}_detector_parameters.yaml`.
- `keyword_lookup` (`soxspipe/commonutils/keyword_lookup.py`) resolves instrument-specific FITS header keyword names from `soxspipe/resources/{soxs,xsh}_keywords.yaml`, so recipe code refers to keyword *aliases* rather than hardcoding ESO header cards.
- `base_recipe.xsh2soxs()` normalizes X-Shooter frames into SOXS-like conventions where needed.

### Key commonutils

- `set_of_files.py` — parses/validates SOF files into frame collections for a recipe.
- `combiner.py`, `image_transformer.py` — frame combination and geometric transforms (rectification, order straightening).
- `create_dispersion_map.py`, `dispersion_map_to_pixel_arrays.py`, `polynomials.py` — wavelength/spatial solution fitting and pixel↔wavelength mapping.
- `detect_continuum.py`, `detect_order_edges.py` — echelle order location.
- `horne_extraction.py` — optimal (Horne) spectral extraction, including skyline-based wavelength-calibration tuning.
- `subtract_background.py`, `subtract_sky.py` — background/sky modeling and removal.
- `flux_calibration.py`, `response_function.py` — instrument response and flux calibration.
- `filenamer.py`, `toolkit.py`, `phase3.py` — product naming, shared helper functions, ESO Phase 3 archive export formatting.

### Test layout

The canonical test tree is the top-level `tests/` directory, and it is the only one `pytest` collects:

- `tests/unit/` — fast, offline, isolated tests.
- `tests/integration/` — contract tests across module boundaries (data organiser, recipe orchestration, SQLite, FITS).
- `tests/real_data/` — opt-in acceptance test against a downloaded archive, gated on `SOXSPIPE_REAL_DATA_DIR`.
- `tests/factories/` — builders for synthetic frames, dataframes, settings, and workspaces.

An older inline tree mirroring the source layout (`soxspipe/recipes/tests/`, `soxspipe/commonutils/tests/`, `soxspipe/tests/`) is deprecated and scheduled for removal. It is excluded from `testpaths`, asserts almost nothing, and only runs against undistributed local data. Do not add tests to it, and do not treat it as a safety net.
